# 채널별 글쓰기 스타일 가이드

이 문서는 같은 원본을 플랫폼별로 어떻게 다르게 작성할지 정의합니다.

유튜브는 글의 문체를 복사하는 기준이 아니라, 주제와 타깃, 포지셔닝을 분석하는 자료로만 사용합니다.

글의 문체와 형식은 플랫폼별 샘플을 기준으로 따로 정의합니다.

## 공통 원칙

- 가독성을 최우선으로 둔다.
- 핵심 주장을 초반에 명확히 제시한다.
- 후츠릿만의 인사이트를 반드시 포함한다.
- 단순 나열보다 문제, 해석, 적용 순서로 구성한다.
- 한 문장에 너무 많은 내용을 담지 않는다.
- 기승전결 없이 구구절절 늘어놓지 않는다.
- 대상 타겟이 한국인이므로 한글로 작성한다.

## 블로그

목적:

- 강사와 저자 포지셔닝
- 기술 구현, 문제 해결, 개념 설명, 인사이트 정리
- 교육 자료로 재활용 가능한 긴 형식 콘텐츠

권장 길이:

- 2,000~4,000자

스타일:

- 입력 메시지의 성격에 맞는 글 형태를 먼저 선택한다.
- 무조건 문어체 평서형 반말로 쓴다.
- 문장 종결은 `다`, `이다`, `한다`, `된다`, `있다`, `없다` 중심으로 쓴다.
- 설명문, 분석문, 기술문서에 가까운 톤을 유지한다.
- `합니다`, `습니다`, `입니다`, `됩니다`, `하세요`, `드립니다` 같은 존댓말 종결을 쓰지 않는다.
- `하면 돼`, `해봐`, `거야`, `거든`, `잖아`, `~해`, `~돼` 같은 대화체 종결을 쓰지 않는다.
- 줄글로 길게 쓰지 않고 `##`, `###`, 목록, 코드 블록으로 구조화한다.
- 구현 요청이면 코드와 실습 과정을 중심으로 구성한다.
- 문제 해결 요청이면 시행착오와 해결 과정을 구체적으로 보여준다.
- 개념 설명 요청이면 독자가 겪는 문제에서 출발해 핵심 개념과 한계를 설명한다.
- 인사이트 요청이면 뉴스, 기술 변화, 시장 흐름에서 후츠릿 관점을 뽑아낸다.
- 코드 블록 아래에 중요한 메소드나 개념 설명을 추가한다.
- 입력에 참고 링크가 있으면 맨 마지막에 `## 참고자료` 섹션을 넣는다.
- 입력에 GitHub 링크가 있으면 기술 구현형 블로그에서 예제 코드 또는 GitHub 저장소로 자연스럽게 연결한다.
- 입력에 GitHub 링크가 없으면 GitHub 링크를 추정하지 않는다.
- 제목에 콜론을 사용한 세부 타이틀을 지양한다.
- "가이드"라는 단어는 꼭 필요할 때만 사용한다.

템플릿 파일:

- `agents/broadcasting/prompts/templates/blog.md`

블로그 유형:

```text
기술 구현형: 설치, 배포, 자동화, 코드, 에러, 워크플로우, API 입력
기술 개념 설명형: RAG, LLM, 하네스, 컨텍스트, 아키텍처, 개념 입력
인사이트/시장 해석형: 뉴스, 인수, 출시, 트렌드, 시장 변화 입력
```

기술 구현형 구조:

```text
문제 상황
-> 결론 먼저 제시
-> 왜 이 문제가 생겼는지
-> 필요한 도구와 개념
-> 단계별 구현
-> 주의점과 삽질 포인트
-> 실제 운영 기준
-> 결론
```

개념 설명형 구조:

```text
익숙한 문제 상황
-> 문제가 생기는 이유
-> 핵심 개념 정의
-> 기본 작동 흐름
-> 한계
-> 다음 단계로 진화한 이유
-> 실무자가 알아야 할 판단 기준
```

인사이트/시장 해석형 구조:

```text
최근 사건 또는 데이터
-> 겉으로 보이는 해석
-> 더 중요한 변화
-> 구조적 원인
-> 앞으로 바뀔 판
-> 실무자에게 필요한 역량
-> 한 문장 결론
```

## LinkedIn

목적:

- AI 강사, 개발자 크리에이터, 기업 교육/컨설팅 포지셔닝
- 기술 변화에 대한 관점 제시
- 전문성과 실무 감각을 동시에 전달

권장 길이:

- 300~800자

스타일:

- 맨 위에는 간결한 제목 한 줄을 둔다.
- 존댓말로 작성한다.
- 짧고 임팩트 있게 시작한다.
- 첫 문장은 설명형보다 대비형으로 쓴다.
- 개인 경험이나 뉴스/사건에서 문제를 끌어온다.
- 단순 정보보다 관점과 판단을 제시한다.
- 문단을 짧게 쪼갠다.
- 핵심 개념은 체크리스트나 연도별 변화로 정리해도 좋다.
- 마지막에는 링크, 질문, CTA, 역할 재정의 중 하나로 마무리한다.
- LinkedIn의 목표는 통찰력을 보여주고 블로그 전문으로 유입시키는 것이다.
- 블로그 발행 URL이 있으면 넣고, 아직 없으면 `[블로그 링크]` 자리표시자를 둔다.
- `블로그 전문:`처럼 불필요한 콜론을 쓰지 않는다.

후츠릿 LinkedIn 패턴:

```text
문제 제기
-> 사건/트렌드/개인 경험
-> 더 중요한 구조 변화
-> 실무자에게 필요한 역량
-> 한 문장 결론
```

템플릿 파일:

- `agents/broadcasting/prompts/templates/linkedin.md`

주의:

- LinkedIn 톤처럼 전문적으로 쓰되 후츠릿만의 인사이트가 꼭 들어가야한다.
- 전문성은 살리되, 알맹이 없는 추상어를 줄인다.
- "AI가 다 해준다"가 아니라 설계와 검증 능력을 강조한다.
- 특히 AI의 엄청난 능력을 소개할땐 여기서 인간이 고민해야하는 부분이 무엇인지 짚어준다.
- `[후츠릿 인사이트]`, `후츠릿의 인사이트`, `실무 적용 포인트` 같은 내부 라벨을 공개 글에 쓰지 않는다.
- 일반론으로 끝내지 말고 `도구 사용량보다 시스템을 설계하고 검증하는 능력에서 차이가 난다`처럼 판단 기준으로 닫는다.

## Discord 뉴스레터

목적:

- `broadcasting` 채널에 타깃 독자용 짧은 뉴스레터 발송
- 블로그/LinkedIn보다 더 빠르게 핵심과 실행 항목 전달
- Discord 메시지에서도 Markdown 제목이 시각적으로 보이게 작성

스타일:

- 존댓말을 사용한다.
- 제목은 짧게 쓴다.
- 제목 다음에는 핵심 내용을 자연스러운 문단으로 쓴다.
- `핵심 요약`, `왜 중요한가`, `바로 해볼 것` 같은 고정 라벨을 일부러 넣지 않는다.
- 실행 항목은 짧은 목록으로만 정리한다.
- 너무 길지 않게 작성한다.
- 참고한 링크가 있으면 맨 아래에 반드시 넣는다.
- 참고 링크가 없으면 `참고 링크` 섹션을 만들지 않고, `참고 자료는 없습니다` 같은 문구도 쓰지 않는다.
- Discord 뉴스레터에는 `{BLOG_URL}` placeholder를 넣지 않는다.
- 내부 평가 점수, 승인 상태, 저장 경로는 독자용 Discord 뉴스레터에 쓰지 않는다.

권장 구조:

```text
## 제목
핵심 문단
의미 문단
- 실행 항목
- 실행 항목
**참고 링크**
```

템플릿 파일:

- `agents/broadcasting/prompts/templates/discord.md`
