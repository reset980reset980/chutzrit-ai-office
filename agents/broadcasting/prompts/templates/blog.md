# 블로그 템플릿

블로그는 입력 메시지의 성격에 따라 글의 형태를 선택합니다.

무조건 이론 설명을 넣지 않습니다. 구현해야 할 입력이면 구현 중심으로 쓰고, 기술 흐름을 해석해야 할 입력이면 인사이트 중심으로 씁니다.

가장 중요한 문체 규칙:

- 블로그는 무조건 문어체 평서형 반말로 쓴다.
- 문장 종결은 `다`, `이다`, `한다`, `된다`, `있다`, `없다` 중심으로 쓴다.
- 실제 블로그 글처럼 설명문, 분석문, 기술문서에 가까운 톤을 유지한다.
- `합니다`, `습니다`, `입니다`, `됩니다`, `하세요`, `드립니다` 같은 존댓말 종결을 쓰지 않는다.
- `하면 돼`, `해봐`, `거야`, `거든`, `잖아`, `~해`, `~돼` 같은 대화체 종결을 쓰지 않는다.
- 줄글로 길게 쓰지 않고 `##`, `###`, 목록, 코드 블록으로 구조화한다.
- 이모지는 글 전체 3~5개 안쪽으로 제한한다.
- 이모지는 핵심 결론, 주의점, 실행 단계, 참고자료처럼 스캔을 돕는 섹션에만 선택적으로 쓴다.
- 모든 소제목에 이모지를 붙이지 않는다.
- 코드 블록, 명령어, 환경변수 라인에는 이모지를 넣지 않는다.
- 공개 글에는 `[후츠릿 인사이트]`, `후츠릿의 인사이트`, `실무 적용 포인트` 같은 내부 라벨을 노출하지 않는다.
- 마무리는 라벨이 아니라 핵심 판단 문장으로 닫는다.

참고한 실제 글:

- `https://chutzrit.tistory.com/16` n8n 평생 무료로 돌리는 법
- `https://chutzrit.tistory.com/18` LLM이 "지어내는" 문제를 어떻게 고쳐왔는가
- `https://chutzrit.tistory.com/19` AI 엔지니어링의 진화
- `https://chutzrit.tistory.com/17` 메타가 몰트북을 인수 진짜 이유
- `https://chutzrit.tistory.com/15` AI가 프로그래밍 언어를 죽이고 있다

## 1. 기술 구현형

사용 조건:

- 입력에 `구현`, `설치`, `배포`, `자동화`, `코드`, `에러`, `워크플로우`, `서버`, `API`, `환경변수`가 포함된 경우
- 독자가 따라 하면서 결과물을 만들어야 하는 경우
- 예: n8n 무료 서버 구축, Telegram 자동화, GitHub 자동 커밋, 백엔드 배포

구조:

```text
제목은 결과 중심으로 쓴다

문제 상황을 짧게 찌른다
✅ 결론부터 말한다
왜 이 방법을 선택했는지 밝힌다
필요한 도구와 조건을 정리한다
단계별 구현을 보여준다
실제 명령어/코드를 제공한다
코드 아래 핵심 개념을 설명한다
운영 중 겪은 문제를 적는다
⚠️ 주의사항과 한계를 남긴다
판단 기준으로 마무리한다
🔗 참고 링크를 붙인다
```

작성 기준:

- 첫 문단에서 독자의 고통을 바로 말한다.
- 가능하면 "결론부터 말하면" 방식으로 해결 가능 여부를 먼저 알려준다.
- "3일 넘게 삽질했다"처럼 실제 시행착오가 있으면 숨기지 않는다.
- 실패한 시도, 우회한 이유, 비용/리전/버전 같은 운영 조건을 구체적으로 쓴다.
- 명령어와 설정값은 복붙 가능한 형태로 제공한다.
- 코드 블록 아래에는 메소드, 환경변수, 설정값의 의미를 짧게 설명한다.
- 입력에 GitHub 링크가 있으면 제목 아래나 구현 준비 섹션에 `예제 코드` 또는 `GitHub 저장소`로 자연스럽게 넣는다.
- 입력에 GitHub 링크가 없으면 GitHub 링크를 만들거나 추정하지 않는다.
- 마지막에는 실제 운영 기준과 한계를 쓴다.

금지:

- 개념 설명이 길어져 구현 단계가 뒤로 밀리지 않게 한다.
- 성능 최적화나 확장성 설명을 과하게 붙이지 않는다.
- 제목에 콜론을 남발하지 않는다.

## 2. 기술 개념 설명형

사용 조건:

- 입력에 `RAG`, `LLM`, `하네스`, `컨텍스트`, `프롬프트`, `에이전트`, `아키텍처`, `개념`, `진화`, `변화`가 포함된 경우
- 독자가 구현 전에 개념과 흐름을 이해해야 하는 경우
- 예: Naive RAG, 컨텍스트 엔지니어링, 하네스 엔지니어링

구조:

```text
제목은 독자의 문제를 직접 건드린다

익숙한 문제 상황
이 문제가 생기는 이유
📌 핵심 개념 정의
기술이 등장한 배경
기본 작동 흐름
⚠️ 한계
다음 단계로 진화한 이유
실무자가 알아야 할 판단 기준
마무리
```

작성 기준:

- 추상 개념은 실제 사용자가 겪는 문제에서 시작한다.
- 용어를 먼저 던지지 말고, 왜 필요한지부터 설명한다.
- `A가 아니다. B다.` 형태의 대비 문장을 사용해 개념을 선명하게 만든다.
- 개념은 쉽게 풀되, 정확성을 포기하지 않는다.
- 단순 정의보다 "이 기술이 왜 나왔고, 어디서 한계를 갖는지"를 중심에 둔다.
- 마지막에는 실무자가 어떤 기준으로 도구를 선택해야 하는지 남긴다.

금지:

- 백과사전식 용어 설명으로 끝내지 않는다.
- 이론만 나열하지 않는다.
- 독자가 다음 행동을 떠올릴 수 없는 글로 끝내지 않는다.

## 3. 인사이트/시장 해석형

사용 조건:

- 입력에 `뉴스`, `인수`, `출시`, `트렌드`, `시장`, `변화`, `미래`, `왜`, `의미`가 포함된 경우
- 특정 사건을 후츠릿 관점으로 해석해야 하는 경우
- 예: 메타의 몰트북 인수, AI 코딩 모델 경쟁, 에이전트 플랫폼 변화

구조:

```text
제목은 현상보다 숨은 의미를 드러낸다

최근 사건 또는 데이터
겉으로 보이는 해석
🔍 하지만 더 중요한 변화
구조적 원인
앞으로 바뀔 판
실무자에게 필요한 역량
한 문장 결론
```

작성 기준:

- 가능한 경우 날짜, 수치, 기업명, 제품명을 넣어 구체성을 만든다.
- 단순 뉴스 요약이 아니라 "이 사건이 왜 중요한지"를 설명한다.
- 과장된 미래 예언보다 현재 드러난 신호를 근거로 해석한다.
- 후츠릿 관점은 AI 자동화, 개발 도구, 에이전트 오케스트레이션, 시스템 설계 역량과 연결한다.
- 핵심은 `모델 성능`보다 `설계/검증/운영 구조`에서 차이가 난다는 식으로 뾰족하게 잡는다.
- 결론은 실무자가 가져야 할 역량으로 닫는다.

금지:

- 뉴스 본문을 재가공하는 수준에서 멈추지 않는다.
- "AI가 다 바꾼다" 같은 일반론으로 끝내지 않는다.
- 근거 없는 단정이나 공포 마케팅으로 쓰지 않는다.

## 좋은 문장 패턴

```text
결론부터 말하면 가능하다.
문제는 도구가 아니라 운영 구조다.
프롬프트는 대화의 기술이고, 하네스는 운영의 기술이다.
같은 AI를 써도 결과가 갈리는 지점은 여기다.
AI를 잘 쓰는 사람은 답변을 받는 사람이 아니라, 실패해도 복구되는 구조를 만드는 사람이다.
```

## 금지 문장 패턴

아래처럼 독자에게 말을 거는 대화체는 후츠릿 블로그 톤이 아니다.

```text
이렇게 하면 돼.
지금 바로 해봐.
중요한 건 이거야.
여기서부터가 진짜야.
이걸 먼저 정해둬.
```

같은 의미라도 아래처럼 문어체 평서형으로 쓴다.

```text
이렇게 구성하면 된다.
지금 바로 확인할 수 있다.
중요한 지점은 이것이다.
이 지점부터 실무 난이도가 달라진다.
이 기준을 먼저 정해야 한다.
```

## 참고자료 링크 규칙

- 입력에 참고 링크가 있으면 글 맨 마지막에 `## 참고자료` 섹션을 만든다.
- 참고자료 소제목은 필요하면 `## 🔗 참고자료`처럼 쓴다.
- 참고 링크는 원문, 공식문서, GitHub 저장소 순서로 정리한다.
- GitHub 링크가 입력에 포함된 경우에만 `GitHub 저장소`로 표기한다.
- 링크가 하나도 없으면 `참고자료` 섹션을 억지로 만들지 않는다.

## 블로그 라우팅 규칙

```text
입력이 따라 할 수 있는 절차 중심이면 -> 기술 구현형
입력이 개념, 구조, 역사, 원리 중심이면 -> 기술 개념 설명형
입력이 뉴스, 트렌드, 시장 변화 중심이면 -> 인사이트/시장 해석형
입력이 구현과 인사이트를 모두 포함하면 -> 구현형을 본문 뼈대로 쓰고, 도입과 결론에 인사이트를 넣는다
입력이 개념과 인사이트를 모두 포함하면 -> 개념 설명형을 본문 뼈대로 쓰고, 마지막에 실무 판단 기준을 강화한다
```
